# Troubleshooting Guide

Common failure modes and their fixes.

## Reading Error Responses

Every API error response (Phase 3.7 centralized error handling) has the shape:

```json
{
  "detail": "Project not found",
  "request_id": "5c8b1d89-ef91-4e98-9f2c-12a3b4c5d6e7"
}
```

- `detail` — human-readable message (generic `"Internal server error"` for
  unhandled 500s unless `DEBUG=true`, to avoid leaking stack traces)
- `request_id` — correlates this response to a line in the structured JSON logs
  (see [operations-guide.md](operations-guide.md#reading-logs))

## Database Connection Errors

**Symptom:** `/status` shows `"postgres": {"healthy": false, ...}`, or the app
fails to start.

| Cause | Fix |
|---|---|
| `DATABASE_URL` unset or malformed | Verify the env var is set exactly as copied from Neon/your Postgres provider |
| Scheme is `postgres://` and driver mismatch | Already handled automatically — `backend/app/database.py` rewrites `postgres://`/`postgresql://` to `postgresql+psycopg://` for the psycopg3 driver used by this project |
| Neon project is idle/suspended (free tier) | Neon free tier suspends idle databases; the first request after idle takes longer to wake it — retry after a few seconds |
| Connection limit exceeded | Check Neon dashboard for the max connections on your plan; reduce backend instance count or use a pooled connection string (Neon provides one) |
| Migrations not applied | Run `python -m alembic upgrade head` manually against `DATABASE_URL` and check the output |

## Redis / AI Gateway Cache Not Working

**Symptom:** `/status` shows `"redis": {"healthy": false, ...}`, or
`/metrics` shows `gemini_cache_hit_rate` staying at 0.

| Cause | Fix |
|---|---|
| `REDIS_URL` unset | Caching is optional — the app runs fine without it, just with a 0% cache hit rate (falls back to a live Gemini call every time). Set `REDIS_URL` to enable. |
| Wrong scheme (`redis://` vs `rediss://`) | Upstash requires TLS — make sure the connection string uses `rediss://`, not `redis://` |
| `redis` Python package missing | Confirm `redis==8.0.1` (or later) is in `requirements.txt` and installed — this was a real bug found during Phase 3.7 review (Phase 3.5 shipped without it, silently falling back to no caching) |
| Redis connection timeout | Check Upstash dashboard for outages; the app degrades gracefully (explanations still work, just uncached) |

## Gemini API Outages / Errors

**Symptom:** Variance explanations return a generic/stub message instead of an
AI-generated one; `/metrics`'s `gemini_requests_total` stops increasing.

| Cause | Fix |
|---|---|
| `GEMINI_API_KEY` unset | Expected — the app intentionally falls back to `StubExplanationProvider`, a deterministic explainer. Not an error. |
| Gemini API outage or rate limit | `agents/explanation_agent.py`'s `GatewayExplanationProvider` catches exceptions from the Gemini call and falls back to the stub automatically — variance data itself is never blocked, only the AI narrative degrades |
| Invalid/expired API key | Check Google AI Studio for key status; rotate per [operations-guide.md](operations-guide.md#rotating-secrets) |

## CORS Errors ("Failed to fetch" in the browser)

**Symptom:** Frontend console shows `Failed to fetch` / `CORS policy blocked`.

| Cause | Fix |
|---|---|
| `CORS_ALLOWED_ORIGINS` doesn't match the actual frontend URL | Check the browser's actual origin (e.g. `https://payverify-ai-app.onrender.com`) and set `CORS_ALLOWED_ORIGINS` on the **backend** to that exact value (comma-separated if multiple), then redeploy the backend |
| `NEXT_PUBLIC_API_BASE_URL` points at the wrong backend URL | This is baked into the frontend bundle at Docker build time — verify it in the Render dashboard, then trigger a rebuild (not just a restart) of the frontend service |
| Testing locally against a deployed backend | Add `http://localhost:3000` to `CORS_ALLOWED_ORIGINS` temporarily |

## Failed Deployments

**Symptom:** Render build fails, or the service crashes on startup.

| Cause | Fix |
|---|---|
| `COPY rules/ rules/: /rules not found` (or similar) during Docker build | The service's Root Directory in the Render dashboard must be empty (repo root) — Blueprint (`render.yaml`) deployments set `dockerContext` correctly automatically; manual dashboard configuration is more error-prone |
| Migration fails on startup (`alembic upgrade head` in `backend/entrypoint.sh`) | Check the deploy logs for the specific migration error; a common cause is a manually-applied schema change that conflicts with an autogenerated migration — reconcile with `alembic stamp <revision>` if the DB is already at the target schema out-of-band |
| Health check never passes | Confirm `healthCheckPath: /health` in `render.yaml` (not `/status` — `/health` has no dependency calls and should always be fast) |

## Authentication Errors

**Symptom:** `401 Unauthorized` on `POST /api/projects` (or other mutating
endpoints) even with a token.

| Cause | Fix |
|---|---|
| `AUTH_ENABLED=false` but calling `/auth/token` | Auth is a no-op by design when disabled — `require_auth` never checks the token. Set `AUTH_ENABLED=true` to actually enforce it. |
| Token expired | Default expiry is 60 minutes (`JWT_EXPIRE_MINUTES`) — request a new token via `POST /auth/token` |
| `JWT_SECRET` changed since the token was issued | All previously-issued tokens are invalidated when the secret rotates — this is expected; re-authenticate |
| `ADMIN_PASSWORD_HASH` not set | `POST /auth/token` returns 401 for all credentials if this env var is empty — set it via `python scripts/hash_password.py` |

## Rate Limiting (429 Too Many Requests)

**Symptom:** `429` responses from `/auth/token` or upload endpoints.

- `/auth/token` is limited to 10 requests/minute per client IP (brute-force
  protection)
- Upload/register endpoints are limited to 20 requests/minute per client IP

This is expected behavior under abuse or aggressive retry loops. If a legitimate
integration needs a higher limit, adjust the `@limiter.limit(...)` decorator in
`backend/app/main.py`.

## Getting a Stack Trace for Debugging (Non-Production Only)

Set `DEBUG=true` to include the raw exception message in 500 responses and
validation error details in 422 responses. **Never enable this in a
production/shared environment** — it can leak internal implementation details.
